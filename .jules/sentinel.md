## 2025-02-27 - [XSS Fix] `innerHTML` Injection in `appendMessage`
**Vulnerability:** A Cross-Site Scripting (XSS) vulnerability was present in the `appendMessage` function of `frontend/js/chat.js` due to the direct assignment of raw, unescaped text to `bubble.innerHTML` when `isRawHtmlForUser` was true.
**Learning:** Even internal formatting assumptions for variables intended as "raw HTML" shouldn't bypass basic security sanitation.
**Prevention:** Always use `DOMPurify.sanitize()` (or a similar sanitization utility) on any dynamically generated content inserted into the DOM via `innerHTML`, even if the source is intended to be safe UI output.
## $(date +%Y-%m-%d) - [XSS Fix: Sanitize KaTeX Fallback Output]
**Vulnerability:** User inputs formatted as math blocks (e.g. `$$ <img src=x onerror=alert(1)> $$`) bypassed DOMPurify because they were temporarily replaced by safe placeholders during sanitization. When the placeholders were replaced back with the raw math content in the HTML, they were injected directly as innerHTML in fallbacks, enabling XSS if KaTeX didn't load or threw an error.
**Learning:** Whenever a pre-processing step shields raw user inputs from a sanitizer (like DOMPurify), those inputs must be meticulously escaped manually before being re-injected into the DOM later.
**Prevention:** Always wrap variables containing potentially untrusted user input with an HTML escaping function (like `escapeHtml()`) before injecting them into HTML strings that will be rendered dynamically in the DOM, especially when circumventing or operating outside the main sanitization pipeline.
## 2025-02-14 - [Insecure CDN Fallback leading to XSS]
**Vulnerability:** The application relied on DOMPurify from a CDN to sanitize user input and AI-generated HTML before injecting it via `innerHTML`. If the CDN failed to load (e.g. network failure or blocked by extensions), the fallback path simply skipped sanitization and injected the raw, untrusted HTML directly into the DOM. This resulted in a Cross-Site Scripting (XSS) vulnerability.
**Learning:** The fallback for a missing security dependency was to disable the security check entirely rather than failing securely. This pattern of "if security check missing, proceed anyway" is a critical anti-pattern.
**Prevention:** Always implement a "fail-secure" or "fail-closed" fallback for security mechanisms. If a required sanitization library is unavailable, the fallback should strictly escape all input (e.g., HTML entity encoding) or block the action entirely, rather than allowing potentially malicious content to execute.
## 2026-08-26 - [Rate Limiting Fix] Missing trust proxy setting
**Vulnerability:** The application is deployed behind a reverse proxy (Render load balancer), but Express wasn't configured to trust it via `app.set('trust proxy', 1)`. As a result, `req.ip` always resolved to the proxy's internal IP address instead of the actual client's IP. This caused all users to share the same rate-limiting bucket in `rateLimitMap`, making the application vulnerable to self-inflicted Denial of Service (DoS) under normal load, and allowing attackers to bypass individual rate limits.
**Learning:** IP-based security controls (like rate limiting) are useless or even harmful if the application doesn't correctly resolve the client's IP address when deployed behind a load balancer.
**Prevention:** Always verify the deployment environment. If the Node.js/Express app runs behind a reverse proxy (like Render, Heroku, Nginx), ensure `app.set('trust proxy', <number_of_hops>)` is explicitly configured so `req.ip` represents the true client.
## 2025-02-27 - [Information Exposure] Server error leakage and Missing Headers
**Vulnerability:** The application was lacking standard HTTP security headers, and the backend error handler in `/api/chat` was leaking sensitive system error structures (via `util.inspect(err)`) directly to the client when a request failed.
**Learning:** Returning full error objects or internal debugging strings to the frontend compromises security by exposing internal system configuration, paths, or third-party API details. Also, missing security headers leaves the app vulnerable to XSS, clickjacking, and MIME-sniffing.
**Prevention:** Implement a defense-in-depth middleware that adds essential security headers (`X-Frame-Options`, `X-Content-Type-Options`, `Strict-Transport-Security`, `X-XSS-Protection`). For error handling, always log detailed errors server-side, but return sanitized, generic error messages to the client.
## $(date +%Y-%m-%d) - [Reverse Tabnabbing Fix] DOMPurify Target Attribute
**Vulnerability:** The application uses DOMPurify to sanitize HTML output but explicitly allows the `target` attribute via `{ ADD_ATTR: ["target"] }`. This configuration exposes the application to Reverse Tabnabbing attacks where a newly opened tab can manipulate the original application page using the `window.opener` object.
**Learning:** Allowing user-supplied `target` attributes in sanitized HTML without also enforcing `rel="noopener noreferrer"` can lead to security vulnerabilities, specifically reverse tabnabbing.
**Prevention:** Added a global `DOMPurify.addHook('afterSanitizeAttributes', ...)` to automatically append the `rel="noopener noreferrer"` attribute to any element that contains a `target` attribute to prevent reverse tabnabbing.
